# 测试执行与证据

测试范围为结构、正反触发、节点、混合交接（如适用）、异常与回归，不生成或执行端到端测试。验证通过仅表示约定范围内的必测项通过，不代表完整业务链路已经实测。

## 测试适配器

代码测试：stdin 为 JSON 输入，stdout 输出唯一 JSON 结果（不要混杂日志），诊断写 stderr。脚本启动成功不能替代业务断言。结构用例实际加载所需依赖或调用脚本帮助；生成时 AST 语法检查不代表依赖可用。

AI/hybrid 测试：适配器调用目标模型执行真实请求，再按 rubric 评审。优先独立模型或人工评审，避免同一模型仅自报高分。stdout 协议：

```json
{
  "result": true,
  "response": "完整模型原始响应或可定位的响应摘录",
  "model": "实际模型标识和版本",
  "reviewer": "评审人或独立评审模型标识",
  "evidence": "具体评分依据，引用原始响应及产物路径",
  "scores": {"evidence_grounding": 1.0, "usefulness": 0.9},
  "tokens": null
}
```

Token 不可观测时用 null；不能编造值。原始调用日志和业务产物保存在当前执行目录，自动进入摘要清单。不得将固定 JSON、关键字匹配、mock 模型或人工猜测当作真实 AI 或路由结果。框架单元测试可以使用模拟适配器，但必须明确隔离并标注。

触发测试执行真实技能选择：提供技能 name/description 与正向/近似无关请求，记录模型是否选择。`result` 为布尔值；用 baseline 调用无 Skill 的同类路由环境。仅搜索描述中的关键词不验证模型触发行为。

AI 测试每次 candidate 和 baseline 使用同一输入和评分标准；至少两次。对照低于业务标准仍是有效对照，只要实际运行且结果可评分。报告保存双方逐次结果和平均分差，不把“有对照”解释为“已经改善”，也不将两次样本解释为统计显著性。

混合测试同时检查真实语义候选及代码交接；额外写确定性反例（类型错误、缺字段、越界、规则冲突），确认无效候选不会进入执行，并覆盖需要人工介入与无需介入的路径。失败业务输入可由适配器捕获预期拒绝并输出 JSON，执行器自身失败使用非零退出。

## 状态与报告

- passed：实际执行且断言/评分满足。
- failed：断言不符、无效 JSON、非零退出或超时。
- blocked：命令/模型/依赖不可用；无有效对照也会阻塞 AI 验证。
- not_run：用例存在但本轮未选择。

选中的案例保存每次证据；任一候选重复失败就使案例失败。可选用例失败不阻止约定必测项通过，但仍展示未解决项。模型、评分、Token 是适配器提供的数据，工具只验证协议与一致性，无法替代对适配器真实性的审查。

报告区分用例生成、静态检查、业务验证。只有必测项全部通过且交付/证据未变才验证通过。成功率分母为已执行的对应案例，执行覆盖率另外呈现，避免用少量已执行案例掩盖阻塞。报告可追溯到需求、节点、分支、Skill 内容摘要及环境。

## 修订

1. 根据失败证据定位原因，修改源文件或项目契约；调整必要业务版本号。
2. `revise --issue '观察到的失败' --change '实际修改'` 记录修改并关联上一轮。
3. `build` 保存新的内容版本，旧交付不覆盖。
4. 先可定向重测，最终全套回归。旧报告不能作为新内容的验收证据。

测试命令继承当前环境及权限。这不是代码沙箱；不自动创建 API 凭证或获得外部写入授权。请按业务上下文核对命令和模型费用，必要时在现成隔离环境运行。运行证据可能含用户输入，选择适当工作目录和访问权限。

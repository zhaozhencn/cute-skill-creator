# 节点执行方式

| 业务特征 | mode | 选择依据与实现 |
| --- | --- | --- |
| 开放输入、答案不唯一 | ai | 目标、证据来源、质量标准和失败边界；保留合理判断空间 |
| 公式、映射、格式或规则明确 | code | 可重复脚本与确定性断言，金额等使用适当精度 |
| 语义判断同时受硬约束 | hybrid | AI 输出结构化候选；代码检查字段、类型、范围、引用和规则，再执行 |

不要因方便而把精确运算交给 AI。不要对开放分析硬编码唯一答案。混合节点记录 `handoff`（候选协议）、`validator`（实际脚本资源路径）；无效候选必须在产生业务副作用前失败。

`depends_on` 表示有向无环依赖，`branches` 枚举需要覆盖的正常/异常业务分支。失败处理应说明中止、修复、重试上限或交给用户的条件，不无限重试外部写入。`human_intervention` 可以是“仅无授权外部发送时请求授权”，也可以是“无需人工介入”，必须符合真实业务权限。

示例：利润分析拆成代码计算利润、AI 基于来源解释变化；字段映射拆成 AI 候选、代码校验/转换。权限是另一个维度，不是 mode 的推导结果。

未要求发送/发布的本地分析只记录本地范围，不因未提供外发授权而增加 critical/pending。只有目标中确实需要且授权不足的操作才构成权限缺口；无关授权未知不阻塞生成。

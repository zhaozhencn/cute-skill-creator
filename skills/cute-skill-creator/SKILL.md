# Cute Skill Creator

把业务需求转化为可执行 Skill，交付需求说明、流程设计、Skill 和可追溯测试报告。以当前用户目标为边界，复用已提供的信息及授权。

## 业务澄清

在独立工作目录建立 `project.json`。首次使用脚本前阅读 [项目契约](references/project-contract.md)，可运行 `python3 scripts/creator.py init --workspace <工作目录> --name <skill-name>` 初始化。

先复用对话、已有需求及资料，统一盘点使用者、目标、成功标准、输入输出、流程分支、规则、工具与权限、正常/边界/失败验收案例中的全部已知缺口。需要提问时，按 [菜单式集中澄清](references/clarification.md) 将待处理问题逐项编号，以菜单选项一次性提交，让用户一次回复；不要逐题发送、逐题等待。信息已充分时直接继续。

需求项记录 `confirmed`、`pending` 或 `assumed`，并保留来源。用户选择即为对应事项的确认，更新原项后直接进入流程设计、生成和验证，不再要求复述或额外确认“是否继续”。非关键部分可记录默认假设；漏答的关键项、新出现的关键依赖或冲突才集中补问，保留其余已确认答案。

每个核心步骤必须能够定义输入、输出、约束和验收方法。影响正确性、权限或验收的未知项必须标为 `critical`；缺失时不能用假设绕过。运行 `check` 获取缺口，区分需要用户决策的业务缺口与可自行补齐的流程/测试契约错误；等待回答时允许继续独立设计。

## 流程设计

按节点记录输入、输出、执行方式及依据、约束、校验、失败处理、人工介入条件，以及依赖和分支。阅读 [执行方式选择](references/execution-guide.md)。开放判断使用 AI；明确计算使用代码；语义判断加严格规则使用混合执行。将同一节点中的判断与计算拆分，或明确候选结构和代码校验交接。

人工批准由授权和操作影响单独决定。混合执行无需自动增加审批。存在已有授权时复用；外部写入只在相应授权范围内执行。只分析用户目标实际需要的权限：未要求外发时记录本地处理范围，不新增发送节点，也不把不存在的发送授权设为关键缺口。

## 生成与验证

根据已充分澄清的流程编写 `instructions`、必要的脚本与参考资料，填写 `resources`。工具负责确定性校验、组装和记录；业务理解及业务代码由你完成，不用空实现代替交付。

测试文件留在工作目录，不复制进生成的 Skill。按 [测试和证据协议](references/testing.md) 编写适配器及用例，覆盖结构、正反触发、节点、混合交接（如适用）、异常与回归。AI 用评分标准和证据评估，至少重复两次，并运行无 Skill 或旧版对照。真实执行条件缺失就记录阻塞，不用模拟输出冒充模型结果。

使用 `python3 <本技能目录>/scripts/creator.py <子命令> --workspace <工作目录>`：

1. `check`：列出缺口及流程/测试契约错误。
2. `build`：生成 `delivery/<内容摘要>/<名称>/`、需求说明、流程设计及内容清单。不会覆盖已有 Skill。
3. `test`：实际执行适配器，记录 stdout、stderr、输入、预期、结果、耗时、模型、Token 和文件摘要。命令具有当前进程权限；执行前核对其来源及用户授权，运行不可信代码需使用已有隔离环境。
4. 失败后修订 `project.json` 或源文件，使用 `revise --issue <问题> --change <修改>` 留痕，再 `build` 和 `test`。保留旧交付与测试记录；支持 `test --case <ID>` 定向诊断，完整交付前重跑全套。
5. `report`：重建最近一次报告。仅当前交付未变且所有必测项实际通过时才标记验证通过。

交付时链接业务说明、流程、Skill、报告与证据。分别陈述“已生成用例”“静态检查通过”“业务效果验证通过”。若有阻塞、未执行或失败，说明具体原因、影响及下一步；不得将用例存在或代码编译通过当作业务成功。
